API 설계서·DB 스키마·아키텍처 문서 작성(설계 단계) 요청에는 사용하지 않는다.

# 요구사항 명세서 작성

## 이 문서가 하는 일

요구사항 명세서는 **"무엇을 만들어야 하는가?"** 에만 답한다. "어떻게 만들 것인가?"는 다음 단계인 설계 문서의 몫이다.

```
요구사항 명세서                         설계 문서
─────────────────────────              ─────────────────────
누가 사용하는가?                        Architecture
무엇을 할 수 있는가?                    API
어떤 화면/흐름인가?             →       DB
어떤 데이터를 다루는가?                 Domain / Class
어떤 규칙이 있는가?                     Sequence
어떤 경우에 실패하는가?                 Security
어떤 제약이 있는가?                     Infrastructure
무엇은 만들지 않는가?
아직 결정하지 않은 것은?
```

이 경계가 중요한 이유: 요구사항 단계에서 API 경로나 테이블 구조를 정해 버리면, 설계 단계의 선택지를 근거 없이 좁히고, 구현하는 사람(사람이든 AI든)이 그것을 "확정된 사실"로 받아들인다. 반대로 요구사항이 모호하면 구현자가 매번 추측해야 하고, 특히 AI는 요청하지 않은 기능을 만들어낸다. 그래서 이 문서는 **무엇을**에 대해서는 최대한 구체적으로, **어떻게**에 대해서는 아무것도 확정하지 않는다.

## 요구사항 vs 설계 — 표현 기준

작성하면서 계속 이 표로 스스로 점검한다.

| 영역 | 요구사항(이 문서에 쓴다) | 설계(이 문서에 쓰지 않는다) |
|------|------------------------|----------------------------|
| 인터페이스 | 운동 목록을 조회할 수 있어야 한다. | `GET /api/v1/exercises` |
| 데이터 | 시스템은 운동 기록의 수행일, 세트별 반복 횟수·중량을 관리해야 한다. | `workout_record` 테이블, `reps INT NOT NULL` 컬럼, FK, 인덱스 |
| 오류 | 다른 사용자의 기록을 수정하려 하면 권한 오류를 반환한다. | `403 Forbidden`, 에러 코드 `E4031` |
| 보안 | 인증된 사용자만 개인 기록에 접근할 수 있어야 한다. | JWT, Spring Security 필터 체인 |
| 외부 연동 | 운동 이미지 같은 파일을 저장하고 조회할 수 있어야 한다. | S3 버킷, presigned URL |
| 삭제 정책 | (정해지지 않았으면) TODO로 남긴다. | `deleted_at` 컬럼으로 soft delete |

"입력: 운동 ID"처럼 **식별자를 개념으로 언급하는 것**은 괜찮다. 필드 타입·컬럼명·JSON 키 이름을 정하는 것이 설계다.

## 작성 절차

1. **입력 파악.** 사용자의 설명과 함께, 관련 기존 문서가 있으면 먼저 읽는다(이 프로젝트는 `docs/requirements/`). 기존 문서와 충돌하는 내용을 발견하면 조용히 덮어쓰지 말고 미결정 사항(TODO)으로 남기거나 사용자에게 알린다.
2. **경계부터 잡는다.** 무엇이 범위 안이고 밖인지가 불분명하면 문서를 쓰기 전에 사용자에게 짧게 묻는다(최대 3~4개 질문). 범위는 명확한데 세부 정책만 모르는 경우에는 묻지 말고 TODO로 남긴 채 진행한다.
3. **템플릿대로 작성한다.** 아래 "문서 템플릿"의 8개 영역 순서를 그대로 따른다. 부분 기능(예: "공유 기능만")이라도 8개 영역을 모두 두되, 해당 없는 영역은 "해당 없음 — 이유"로 한 줄만 쓴다. 영역을 통째로 빼면 검토자가 "빠뜨린 건지 해당이 없는 건지" 구분할 수 없다.
4. **지어내지 않는다.** 사용자가 말하지 않은 정책 수치(응답 시간, 보관 기간, 요청 제한, 토큰 만료 시간 등)나 기능을 임의로 확정하지 않는다. 필요한 항목이면 TODO로 남기고, 업계 통상값을 제안하고 싶으면 `(제안, 확정 필요)`라고 표시한다. 그럴듯한 숫자를 지어내면 아무도 검증하지 않은 채 구현까지 흘러간다.
5. **자체 점검 후 저장.** 맨 아래 "완료 전 점검"을 통과시킨 뒤 저장한다. 사용자가 경로를 지정하지 않으면 `docs/requirements/<주제>.md`로 저장한다(예: `docs/requirements/workout-sharing.md`).
6. **보고.** 저장 경로, 기능 요구사항 개수, 미결정 사항(TODO) 목록을 짧게 알려준다. TODO는 사용자가 다음에 결정해야 할 일이므로 빠짐없이 보여준다.

## ID 체계

모든 요구사항에 ID를 붙이는 이유는 **요구사항 → 설계 → 구현 → 테스트**를 나중에 연결하기 위해서다. 설계 문서, 커밋, 테스트 이름에서 이 ID를 참조하게 된다. 한 번 부여한 ID는 바꾸거나 재사용하지 않는다(삭제된 요구사항은 "폐기"로 표시).

| 대상 | 형식 | 예 |
|------|------|-----|
| 기능 요구사항 | `REQ-<도메인>-NNN` | REQ-EXERCISE-001 |
| 화면 | `<화면 접두어>-NNN` | EX-001 (운동), AUTH-001 (로그인) |
| 인터페이스 요구사항 | `IF-<도메인>-NNN` | IF-EXERCISE-001 |
| 데이터 요구사항 | `DATA-NNN` | DATA-001 |
| 비즈니스 규칙 | `BR-NNN` | BR-001 |
| 예외/오류 | `ERR-NNN` | ERR-001 |
| 비기능 요구사항 | `NFR-<분류>-NNN` | NFR-PERF-001, NFR-SEC-001 |
| 미결정 사항 | `TODO-NNN` | TODO-001 |

화면 접두어 `EX`는 운동(Exercise)에 쓰이므로, 예외/오류에는 `ERR`를 쓴다. 이 프로젝트에 이미 쓰는 접두어가 있으면 그것을 따른다.

## 03. 사용자 시나리오 / 화면 흐름

### 3.1 시나리오: <시나리오명>
사용자의 행동 순서를 흐름으로 그린다. 화면은 `[화면명]`, 사용자 행동/시스템 처리는 괄호 없이 쓴다.

```
[운동 목록 화면]
        ↓
사용자가 운동을 선택한다.
        ↓
[운동 기록 화면]
        ↓
세트 추가
        ↓
운동 완료
        ↓
운동 기록 저장
        ↓
[운동 결과 화면]
```

### 3.2 화면 정의
흐름에 등장한 모든 화면을 정의한다. UI 컴포넌트·레이아웃·색상은 쓰지 않는다.

#### EX-001 운동 목록
- 진입 조건:
  - 로그인 완료
- 사용자 행동:
  - 운동 선택
  - 운동 검색
- 시스템 동작:
  - 운동 목록을 조회한다.
- 화면 데이터:
  - 운동 ID
  - 운동명
  - 운동 이미지
  - 최근 수행일
- 다음 화면:
  - 운동 기록 화면 (EX-002)
- 관련 요구사항: REQ-EXERCISE-00N

## 04. 기능 요구사항

### 4.1 기능 목록
| ID | 기능명 | 사용자 | 관련 화면 |
|----|-------|-------|----------|
| REQ-EXERCISE-001 | 운동 기록 등록 | 일반 사용자 | EX-002 |

### 4.2 기능 상세
기능마다 아래 10개 항목을 모두 채운다. 해당 없는 항목은 "없음"으로 쓴다(빈칸으로 두면 누락인지 해당 없음인지 알 수 없다).

#### REQ-EXERCISE-001 운동 기록 등록
- **목적:** 사용자가 수행한 운동을 기록할 수 있어야 한다.
- **사전 조건:**
  - 로그인된 사용자여야 한다.
  - 선택한 운동이 존재해야 한다.
- **사용자 행동:**
  1. 운동을 선택한다.
  2. 세트별 반복 횟수와 중량을 입력한다.
  3. 운동 완료를 누른다.
- **입력:**
  - 운동 ID
  - 수행 날짜
  - 세트 정보 (세트별 반복 횟수, 중량)
- **처리 규칙:**
  - 입력된 운동 기록을 저장한다.
  - 해당 사용자의 기록으로 저장한다.
  - 반복 횟수는 1 이상이어야 한다. (BR-003)
  - 중량은 0 이상이어야 한다. (BR-005)
- **결과:**
  - 운동 기록이 생성된다.
- **예외:**
  - 로그인하지 않은 경우 인증 오류를 반환한다. (ERR-001)
  - 존재하지 않는 운동이면 등록할 수 없다. (ERR-002)
- **관련 화면:** EX-002, EX-003

### 4.3 인터페이스 요구사항
시스템이 외부(클라이언트)에 제공해야 하는 기능의 **필요성**만 정의한다. HTTP 메서드, URL, 요청/응답 형식은 설계 단계에서 정한다.

| ID | 인터페이스 요구사항 | 관련 기능 |
|----|-------------------|----------|
| IF-EXERCISE-001 | 운동 목록을 조회할 수 있어야 한다. | REQ-EXERCISE-00N |
| IF-EXERCISE-002 | 특정 운동의 상세 정보를 조회할 수 있어야 한다. | REQ-EXERCISE-00N |

## 05. 데이터 요구사항
시스템이 **어떤 데이터를 관리해야 하는지**를 정의한다. 테이블·컬럼·타입·키·인덱스는 정하지 않는다.

#### DATA-001 운동 기록
- 설명: 사용자가 특정 날짜에 수행한 운동 한 건
- 관리해야 하는 정보: 기록한 사용자, 운동, 수행 날짜, 세트 정보(세트별 반복 횟수·중량), 완료 여부
- 관계: 한 명의 사용자에 속한다. 하나 이상의 세트를 가진다.
- 생명주기: 운동 시작 시 생성 → 완료 시 수정 불가 → 사용자 요청 시 삭제 (삭제 방식은 TODO-001)
- 관련 규칙: BR-001, BR-002

## 06. 비즈니스 규칙 / 예외

### 6.1 비즈니스 규칙
기능과 무관하게 항상 지켜져야 하는 규칙을 한 문장씩 쓴다.

- **BR-001** 운동 기록은 자신의 기록만 수정할 수 있다.
- **BR-002** 완료된 운동 기록은 수정할 수 없다.
- **BR-003** 운동 세트의 반복 횟수는 1 이상이어야 한다.
- **BR-004** 운동 기록의 수행일은 미래일 수 없다.

### 6.2 예외 / 오류 요구사항
정상 흐름만 정의하면 구현자가 실패 상황을 매번 추측하게 된다. "어떤 상황에서 → 시스템이 어떻게 반응하는가"를 쓴다. HTTP 상태 코드는 확정하지 않고 "인증 오류", "권한 오류", "찾을 수 없음 오류", "입력값 오류" 수준으로 쓴다.

| ID | 상황 | 시스템 동작 | 관련 |
|----|-----|-----------|------|
| ERR-001 | 로그인하지 않은 사용자가 운동 기록을 요청한다. | 인증 오류를 반환한다. | REQ-EXERCISE-001 |

- **포함:** <이번 범위에 들어가는 기능 영역>
- **제외:** <이번에 만들지 않는 것. 예: 소셜 공유, 운동 추천, 결제, 관리자 통계 대시보드>

### 8.2 제약사항
요구사항 자체에 걸린 제약(일정, 기존 시스템과의 호환, 법/정책, 이미 결정된 사실 등)을 쓴다.
- <예: 기존 운동 기록 데이터와 호환되어야 한다.>

### 8.3 미결정 사항
아직 결정하지 않은 것은 억지로 정하지 않고 명시한다. 각 항목에 영향을 받는 요구사항 ID를 적는다.

## 완료 전 점검

저장하기 전에 하나씩 확인한다. 걸리는 항목이 있으면 고친 뒤 저장한다.

**9개 질문에 답하는가**
- 누가 사용하는가(02) / 무엇을 할 수 있는가(01, 04) / 어떤 화면·흐름인가(03) / 어떤 데이터를 다루는가(05) / 어떤 규칙이 있는가(06.1) / 어떤 경우에 실패하는가(06.2) / 어떤 제약이 있는가(07, 08.2) / 무엇은 만들지 않는가(08.1) / 아직 결정하지 않은 것은(08.3)

**구조와 연결**
- 8개 영역이 순서대로 모두 있다(해당 없음은 이유와 함께 명시).
- 모든 기능 요구사항에 10개 항목(ID, 기능명, 목적, 사전 조건, 사용자 행동, 입력, 처리 규칙, 결과, 예외, 관련 화면)이 있다.
- 기능의 "관련 화면"에 적힌 화면 ID가 03장에 모두 정의되어 있고, 흐름에 나온 화면도 모두 정의되어 있다.
- 본문에서 참조한 BR/ERR/TODO ID가 모두 실제로 존재한다.
- 권한 규칙이 역할 이름 나열에 그치지 않고 "본인 것만", "어떤 상태일 때만" 같은 조건까지 있다.

**설계가 섞이지 않았는가**
- HTTP 메서드나 URL 경로(`GET`, `/api/...`)가 없다.
- HTTP 상태 코드(`401`, `403`, `404` 등)가 없다.
- 테이블명, 컬럼명, 데이터 타입, PK/FK, 인덱스가 없다.
- 특정 프레임워크·라이브러리·클라우드 제품명이 없다(사용자가 이미 확정된 제약으로 준 경우는 8.2에만 쓴다).

**지어내지 않았는가**
- 사용자가 주지 않은 수치·정책이 확정된 것처럼 쓰여 있지 않다(TODO 또는 `(제안, 확정 필요)`).
- 사용자가 요청하지 않은 기능이 범위에 들어가 있지 않다.
