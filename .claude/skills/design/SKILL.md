"무엇을 만들지" 정의하는 요구사항 작성에는 requirements 스킬을, 실제 코드 작성에는 사용하지 않는다.

# 설계 문서 작성

## 이 문서가 하는 일

```
요구사항 명세서 (What)  →  설계 문서 (How)  →  테스트 문서 (Verify)
docs/requirements/         docs/design/          docs/test/
무엇을 만들어야 하는가?      그것을 어떻게 만들 것인가?   제대로 만들어졌는가?
```

요구사항 명세서는 일부러 API 경로, 테이블, 상태 코드를 정하지 않았다. 설계 문서는 정반대다. **여기서 구체적으로 확정해야 한다.** URL, HTTP 상태 코드, 필드 이름, 컬럼 타입, 인덱스, 패키지 구조까지 정한다. 설계가 모호하면 구현하는 사람(사람이든 AI든)이 매번 추측하고, 기능마다 다른 방식으로 만들어진다.

동시에 설계는 요구사항을 **넘어서면 안 된다.** 요구사항에 없는 API, 컬럼, 기능을 "있으면 좋으니까" 넣으면 그대로 구현되고 유지보수 부담이 된다. 그래서 이 스킬의 중심은 **추적성**이다. 모든 요구사항이 설계 어딘가에 반영되고, 모든 설계 요소가 어떤 요구사항 때문에 존재하는지 설명할 수 있어야 한다.

## 핵심 원칙

1. **요구사항이 근거다.** 설계 요소(API, 테이블, 컬럼, 에러 코드, 인덱스)마다 근거가 되는 요구사항 ID를 단다. 근거가 없으면 만들지 않는다. 구현상 꼭 필요한데 요구사항에 직접 대응하지 않는 것(예: 목록 조회용 인덱스, 공통 응답 형식)은 어떤 요구사항을 지키기 위한 것인지 적는다(예: NFR-PERF-002를 위해).
2. **요구사항을 고치지 않는다.** 설계하다가 요구사항의 빈틈, 모순, 실현 불가능한 점을 발견하면 설계에서 조용히 정해 버리지 않는다. 부록 C "요구사항 피드백"에 적고 사용자에게 알린다. 요구사항 수정은 requirements 스킬의 몫이다. 요구사항의 미결정 사항(TODO)이 아직 열려 있어 설계할 수 없는 부분은 "보류"로 표시한다.
3. **실제 코드베이스가 기준이다.** 기술 스택, 패키지 루트, 빌드 도구, DB 마이그레이션 방식은 예시나 일반론이 아니라 저장소에서 읽는다(`build.gradle.kts`, `src/` 구조, `src/main/resources/application.yaml`, `src/main/resources/db/`). 이미 들어 있는 의존성이 서로 겹치거나(예: JPA와 jOOQ를 함께 사용) 필요한 의존성이 빠져 있으면(예: 인증이 필요한데 보안 라이브러리가 없음), 그 사실을 드러내고 결정한다.
4. **결정에는 이유를 남긴다.** 기술 스택, 아키텍처, 인증 방식, 삭제 방식, 상태 코드 정책처럼 대안이 있는 선택은 설계 결정(DEC)으로 기록한다. "무엇을 골랐고, 왜 골랐고, 무엇을 버렸는지" 남겨야 나중에 바꿀 때 근거를 따질 수 있다. 기술 스택도 나열만 하지 않고 선택 이유를 쓴다.
5. **전체 먼저, 기능은 필요할 때 상세하게.** 모든 기능이 공유하는 공통 설계는 한 번만 잡는다. 기능 설계는 지금 구현할 기능부터 상세하게 쓴다. 아직 구현하지 않을 기능까지 미리 세세하게 설계하면 요구사항이 바뀔 때 버려진다.
6. **기능 설계는 기술 중립으로 쓴다.** 언어, 프레임워크, DB 제품은 언제든 바뀔 수 있다. 기능 설계에 특정 기술의 문법이나 이름(어노테이션, DB 전용 타입·구문, 라이브러리 클래스, 소스 파일 경로)이 들어가면, 스택이 바뀔 때 모든 기능 설계를 다시 써야 한다. 그래서 기능 설계는 공통 설계가 정의한 **기술 중립 용어**(논리 타입, 제약 종류, 동시성·트랜잭션 개념, 컴포넌트 역할)로만 쓰고, 그 용어가 지금 스택에서 무엇으로 구현되는지는 공통 설계의 **기술 대응표**(10장)에만 둔다. 스택을 바꾸면 공통 설계 1.4와 10장만 고치면 된다.
   기술 중립이 "보장을 흐리게 쓰라"는 뜻은 아니다. "사용자당 진행 중 세션은 동시 요청에서도 하나"처럼 **무엇을 보장해야 하는지**는 정확히 쓴다. 그래야 DB를 바꿀 때 새 DB에서 그 보장을 무엇으로 지킬지 판단할 수 있다. HTTP·JSON 기반 API 계약, 테이블·컬럼·인덱스 같은 관계형 개념, JWT 같은 표준 프로토콜은 특정 제품에 묶이지 않으므로 기능 설계에 써도 된다.

## 문서 구성

설계 문서는 두 종류다.

| 파일 | 내용 | 작성 시점 |
|------|------|----------|
| `docs/design/architecture.md` | **공통 설계**: 시스템 아키텍처, 기술 중립 용어(논리 타입·제약·동시성 개념·컴포넌트 역할), API·데이터 규칙, 인증·보안 방식, 에러 정책, 비기능 공통 대응. **기술에 묶인 내용은 1.4(기술 스택), 10장(기술 대응표, 코드 구조), 그리고 기술 선택에 관한 결정·미결정 기록(부록 A·B)에만** 둔다 | 첫 기능을 설계할 때 한 번. 이후 바뀔 때만 갱신 |
| `docs/design/<기능>.md` | **기능 설계**: 요구사항 명세서 하나에 대응한다. 파일 이름도 같게 한다(예: `docs/requirements/workout-session.md` → `docs/design/workout-session.md`). 전부 기술 중립 용어로 쓴다 | 기능을 구현하기 전에 |

기능 설계는 아래 템플릿의 10개 영역을 모두 둔다. 공통 설계에서 이미 정한 부분은 다시 쓰지 말고 "공통 설계 N장을 따른다"로 참조한 뒤, **이 기능에서 추가되거나 달라지는 것만** 쓴다. 영역을 통째로 빼면 검토자가 빠뜨린 것인지 해당이 없는 것인지 구분할 수 없으므로, 해당이 없으면 "해당 없음 — 이유" 한 줄을 남긴다.

## 작성 절차

1. **입력을 읽는다.**
   - 대상 요구사항 명세서 전체. 폐기된 ID(취소선, "폐기")는 설계 대상에서 뺀다.
   - `docs/design/architecture.md`가 있으면 그것.
   - 저장소: 빌드 파일, `src/` 패키지 구조, 설정 파일, 기존 마이그레이션, 기존 코드의 이름 규칙.
   - 사용자가 Figma 링크를 주면 Figma 도구로 해당 화면을 읽어 4장(화면/API 연계)의 근거로 쓴다. 요구사항의 화면 정의와 Figma가 다르면 부록 C에 적는다.
2. **요구사항을 점검한다.** 살아 있는 요구사항 ID를 모두 목록으로 뽑는다(REQ, BR, ERR, NFR, IF, DATA, 화면 ID). 열린 TODO가 있으면 어떤 ID의 설계를 막는지 확인한다. 설계를 막는 TODO가 있으면 시작 전에 사용자에게 묻거나 그 부분을 보류로 두고 진행한다.
3. **공통 설계를 확인한다.** `architecture.md`가 없으면 먼저 작성한다. 기술 스택처럼 되돌리기 어려운 결정 중 저장소만 보고 정할 수 없는 것(예: 인증 방식, JPA와 jOOQ 역할 분담)은 짧게 묻는다(최대 3~4개). 물어볼 필요가 없는 것은 이유와 함께 결정하고 DEC로 남긴다.
4. **기능 설계를 작성한다.** 아래 템플릿을 따른다. 요구사항에 적힌 숫자와 조건(범위, 상한, 시간)은 설계의 검증 규칙, 컬럼 타입, 제약 조건에 **그대로** 옮긴다. 다른 숫자를 쓰고 싶다면 부록 C로 보낸다. 공통 설계의 용어로 표현할 수 없는 개념이 필요하면(예: 새로운 종류의 제약), 먼저 공통 설계에 용어를 정의하고 10장 기술 대응표에 구현 방법을 추가한 뒤 기능 설계에서 그 용어를 쓴다.
5. **추적성을 맞춘다.** 1.6 추적표에서 살아 있는 요구사항 ID가 하나도 빠지지 않았는지, 반대로 근거 없는 설계 요소가 없는지 확인한다.
6. **완료 전 점검 후 저장한다.** 맨 아래 점검 목록을 통과시킨 뒤 저장한다.
7. **보고한다.** 저장 경로, API 수, 테이블 수, 이번에 내린 설계 결정(DEC)과 이유, 설계 미결정 사항(D-TODO), 요구사항 피드백을 짧게 알린다. 요구사항 피드백은 사용자가 요구사항을 고칠지 결정해야 하므로 빠짐없이 보여준다.

## 설계 쪽 ID 체계

요구사항 ID는 그대로 참조하고, 설계 요소에는 아래 ID를 붙인다. 코드, 커밋, 테스트에서 이 ID로 설계를 가리키게 된다. 한 번 붙인 ID는 바꾸거나 재사용하지 않는다.

| 대상 | 형식 | 예 |
|------|------|-----|
| API | `API-<도메인>-NNN` | API-WORKOUT-001 (`POST /api/v1/workout-sessions`) |
| 설계 결정 | 공통 `DEC-ARCH-NNN`, 기능 `DEC-<도메인>-NNN` | DEC-ARCH-001 |
| 설계 미결정 | 공통 `D-TODO-ARCH-NNN`, 기능 `D-TODO-<도메인>-NNN` (요구사항의 `TODO-NNN`과 구분) | D-TODO-ARCH-001 |
| 에러 코드 | `UPPER_SNAKE_CASE` 문자열 | WORKOUT_SESSION_NOT_FOUND |
| 테이블 | 실제 테이블 이름 | workout_session |

## 공통 설계 템플릿 (`docs/design/architecture.md`)

아래 기능 설계 템플릿과 같은 10개 영역을 쓰되, 다음을 **모든 기능에 공통인 수준**으로 확정한다.

- **1장:** 대상 시스템, 기술 스택 표(구성 요소, 버전, 선택 이유, 버린 대안), 공통 설계 원칙. **기술 제품 이름은 1.4, 10장, 기술 선택에 관한 부록 A·B 항목에만** 나온다.
- **2장:** 시스템 구성도, 컴포넌트 역할(API 진입점, 서비스, 저장소, 조회 저장소 등)과 책임, 서버·네트워크·배포 구조, 외부 시스템 연계 방식, 동시성·트랜잭션 개념(예: 변경 잠금, 독립 트랜잭션, 조건부 일괄 갱신)
- **5장:** URL 규칙(`/api/v1/` 접두어, 복수형 명사, kebab-case), JSON 필드 규칙(camelCase 등), 날짜·시간 형식(ISO-8601, UTC 저장), 페이지 나누기 규칙(요청 파라미터, 응답 형태)
- **6장:** 논리 타입(ID, 정수, 소수(p,s), 문자열(n), 날짜, 시각, 열거 등)과 제약 종류(유일, 조건부 유일, 조건 검사, 참조와 삭제 동작, 인덱스, 조건부 인덱스)의 정의, 테이블·컬럼 이름 규칙, 공통 컬럼, 기본 삭제 정책, 스키마 변경 원칙
- **7장:** 인증 흐름 전체(로그인 → 토큰 발급 → 검증 → 재발급), 토큰과 쿠키 정책, 사용자별 데이터 접근 제한 방식, 비밀번호 처리, CORS, CSRF, 요청 수 제한, 로그에 남기지 않을 정보
- **8장:** 에러 응답 형식, 상태 코드 정책, 공통 에러 코드, 예외를 응답으로 바꾸는 위치(컴포넌트 수준)
- **9장:** 공통 성능·확장성·가용성·보안 대응(무상태 서버, 백업, 로그 형식)
- **10장:** **기술 대응표**(2·6장의 용어와 검증·시간대·정적 파일·테스트 등이 현재 스택에서 무엇으로 구현되는지), 패키지 구조와 계층별 책임, 이름 규칙, 테스트 도구. 스택을 바꾸면 1.4와 이 장만 고친다.

상태 코드 정책의 기본안은 아래와 같다. 바꾸면 DEC로 남긴다.

| 상태 코드 | 용도 |
|----------|------|
| 400 | 입력값 검증 실패 (형식, 범위, 필수값) |
| 401 | 인증 실패 (토큰 없음, 만료, 위조) |
| 403 | 인가 실패 (다른 사용자의 데이터, 권한 없음) |
| 404 | 대상 없음 |
| 409 | 현재 상태와 충돌하는 요청 (이미 완료됨, 이미 진행 중인 것이 있음 등 비즈니스 상태 위반) |
| 500 | 예상하지 못한 서버 오류 (내부 정보는 응답에 넣지 않음) |

## 기능 설계 템플릿 (`docs/design/<기능>.md`)

`<...>`는 채울 부분이다. 예시 내용은 형식을 보여주기 위한 것이므로, 실제로는 대상 요구사항과 저장소에 맞게 채운다.

````markdown
# <기능명> 설계 문서

- 문서 버전: v0.1

## 3. 기능 설계

### 3.1 기능 목록
| 요구사항 ID | 기능 | API | 주요 계층 |
|------------|-----|-----|----------|
| REQ-WORKOUT-001 | 운동 세션 시작 | API-WORKOUT-001 | WorkoutSessionService.start |

### 3.2 기능별 처리 흐름
요구사항의 "처리 규칙"을 구현 단계로 풀어 쓴다. 검증 순서, 권한 확인 위치, 트랜잭션 범위, 반환값까지 적는다.

#### REQ-WORKOUT-001 운동 세션 시작
1. 인증된 사용자 ID를 얻는다. 없으면 401 (ERR-001).
2. 해당 사용자의 진행 중 세션을 조회한다. 있으면 409 `WORKOUT_SESSION_ALREADY_IN_PROGRESS` (BR-011, ERR-011).
3. 세션을 `IN_PROGRESS` 상태, 시작 시각 = 현재 시각(UTC)으로 저장한다. (트랜잭션 시작~끝)
4. 동시에 두 요청이 들어와 2를 모두 통과한 경우, 조건부 유일 제약(6.2) 위반을 409로 바꾼다.
5. 201과 생성된 세션을 반환한다.

### 3.3 주요 시나리오
요구사항 3장의 시나리오를 클라이언트 ↔ API ↔ DB 순서로 보여준다.
```
App            API                         DB
 │ 운동 시작     │                            │
 │────────────▶│ 진행 중 세션 조회             │
 │             │──────────────────────────▶│
 │             │ 세션 저장                    │
 │             │──────────────────────────▶│
 │◀────────────│ 201                        │
```

### 3.4 상태 변화
```
[IN_PROGRESS] ──사용자 완료(REQ-WORKOUT-002)──▶ [COMPLETED]
      │
      └──6시간 경과, 세트 있음(REQ-WORKOUT-006)──▶ [COMPLETED]
      └──6시간 경과, 세트 없음──▶ (삭제)
```
상태별로 허용되는 작업을 표로 정리한다.

### 3.5 비즈니스 규칙 구현
요구사항의 BR 하나하나를 어디서 어떻게 강제하는지 정한다. 중요한 규칙은 애플리케이션 검증과 DB 제약을 함께 둔다(동시 요청, 다른 경로로 들어온 데이터까지 막기 위해). 방법은 공통 설계의 용어로 쓴다(어노테이션·SQL 구문 대신 "요청 검증", "조건 검사 제약" 등).

| BR ID | 규칙 | 강제 위치 | 방법 | 위반 시 |
|-------|-----|----------|-----|--------|
| BR-003 | 반복 횟수 1~1,000 정수 | 요청 검증, DB | 요청 검증(필수, 정수, 1~1,000) + 조건 검사 제약 `repetitions BETWEEN 1 AND 1000` | 400 VALIDATION_FAILED |
````

## 완료 전 점검

저장하기 전에 하나씩 확인한다. 걸리는 항목이 있으면 고친 뒤 저장한다.

**추적성**
- 요구사항의 살아 있는 ID(REQ, BR, ERR, NFR, IF, DATA, 화면)가 1.6 추적표에 빠짐없이 있다. 폐기된 ID는 쓰지 않았다.
- 모든 API, 테이블, 인덱스, 에러 코드에 근거 요구사항 ID가 있다.
- 요구사항 8.1에서 제외한 기능을 위한 API, 컬럼, 화면 연계가 없다.

**요구사항 충실도**
- 모든 BR이 3.5에서 강제 위치와 방법을 가진다.
- 모든 ERR이 8.2에서 에러 코드와 상태 코드를 하나씩 가진다.
- 요구사항의 숫자(범위, 상한, 시간, 개수)가 검증 규칙·컬럼 타입·제약 조건과 정확히 일치한다. 예를 들어 소수점 둘째 자리까지 허용하는 0~1,000이면 컬럼과 검증이 그 범위를 모두 담는다.
- 요구사항과 다르게 설계한 곳이 있다면 부록 C에 적었다.

**구체성**
- 모든 API에 Method, URL, 인증, Request, Response 예, 성공 상태 코드, Validation, Errors가 있다.
- 모든 테이블 컬럼에 타입, Null 여부, 근거가 있고 PK/FK/Unique/Check가 정해져 있다.
- 모든 인덱스에 대상 조회가 적혀 있다.
